# Species Detail Pages — Options, Tradeoffs, Recommendation

## Goal
Add a dedicated page per species (e.g. *Aphonopelma seemanni*) that lets you understand **why** it’s flagged (🔥/⚠️/❌), and see **price/wishlist/stock history** in a cleaner UX than per-cell sparklines.

Constraints from this repo:
- Static site generated by Python + Jinja templates
- “Markdown-first” architecture: analysis narrative is Markdown → HTML
- Conservative analysis philosophy: avoid noise, keep outputs explainable
- Existing building blocks: history CSV, summary stat cards, SVG sparklines, filter/sort/search JS

## What the detail page should answer
For a species, quickly show:
1. **Current classification** (breeder signal / dealer risk) + short explanation “why”
2. **Stock behavior** summary (IN/OUT streaks, restock speed, availability reliability)
3. **Price trend** over time (ideally last 12–26 runs by default)
4. **Wishlist** (level + delta/momentum) with conservative bounds
5. **Size variants** (if applicable) without confusing charts
6. A clear “back to table” and (optionally) “open SpiderShop listing” link

## Data inputs (already in your artifacts)
- `spidershop_spiderlings_history.csv`: time series of price/wishlist by scrape datetime
- `breeder_opportunity_table.csv` / `dealer_supply_risk_table.csv`: current classification outputs
- `spidershop_spiderlings_scrape.csv`: current run snapshot (optional)

## URL + routing choices (static site)
A detail page needs a stable URL. Typical patterns:
- `/species/aphonopelma-seemanni.html`
- `/species/Aphonopelma_seemanni.html` (less pretty)

Recommendation for stability: **slug** from scientific name, lowercase, hyphen-separated.

## Options

### Option A — “Inline expansion” (no new pages)
**What:** Clicking species expands a hidden panel inside the table row, showing a bigger chart + some history.

Pros:
- Fastest UX win; minimal new navigation
- Avoids generating many new pages

Cons:
- Tables become heavy/complex on mobile
- Hard to deep-link/share a species view
- Row expansion + sorting/filtering interactions get tricky

Best when:
- You want the simplest improvement and are OK without shareable URLs

---

### Option B — Static pre-generated per-species pages (recommended)
**What:** Website generator emits `species/<slug>.html` for each species seen in the current run (or in history).
Page is rendered with Jinja, same layout as existing pages.

Implementation variations:
- **B1: SVG charts only** (no external chart libs). Use your existing SVG sparkline approach, just “bigger.”
- **B2: Chart.js via CDN** for nicer interaction (zoom, tooltips) but introduces a dependency.

Pros:
- Deep-linkable, simple navigation, very “static-site friendly”
- Easy to test deterministically (HTML structure snapshots or targeted assertions)
- No complicated table JS interplay required

Cons:
- More generated files (potentially hundreds)
- Need thoughtful handling for multiple sizes per species

Best when:
- You want maintainability + shareable URLs + conservative, explainable outputs

---

### Option C — Single dynamic page + JSON dataset
**What:** Generate one page `/species.html` and a JSON blob of history; page renders different species based on query string (e.g. `?s=aphonopelma-seemanni`).

Pros:
- Only 1 HTML page; fewer output files
- Potentially smoother UX once loaded

Cons:
- More JavaScript complexity
- Harder to keep “markdown-first” feel
- More places for subtle bugs (parsing, escaping, routing)

Best when:
- You want “app-like” behavior and don’t mind a bigger JS surface

---

### Option D — Markdown-per-species pages (manual content)
**What:** You create markdown files per species, compile them.

Pros:
- Great if you want editorial writeups for a short list

Cons:
- Not scalable for many species
- Doesn’t naturally include computed charts/history tables

Best when:
- Only a curated Top N species need writeups

---

### Option E — “Mini cards” only (no charts)
**What:** Detail page shows summary stats and a small, simple “last N runs” table.

Pros:
- Very conservative, explainable, minimal visual noise
- Zero charting complexity

Cons:
- Less intuitive trend reading than a chart

Best when:
- You want the simplest “detail page” step first

## Key design decisions to make (regardless of option)

### 1) Which species get a page?
- **Current table species only** (recommended first step): pages only for species in breeder/dealer tables.
- All historical species: might create many pages including irrelevant/obsolete entries.

### 2) Size handling (critical)
Recommended UX:
- Default view: **aggregate view** showing the size used in the matrix row (or “most common size”).
- Then show a **Size selector** (“1.0cm”, “1.5cm”, …) to switch chart/table.

### 3) Default time window
- Default: last **12–26 runs** (matches weekly cadence + conservative interpretation)
- Offer “show all history” as a secondary action

### 4) Chart approach
- Prefer **SVG (B1)** first: consistent with existing sparklines, no new deps, deterministic output.
- Keep tooltips optional; avoid “pretty” interactions that imply precision.

### 5) “Why” explanation block
Put a compact explanation near the top:
- “Signal: 🔥 because OUT for X runs, slow restock, rising wishlist”
- Always include the conservative caveat: “Single-run changes are treated as noise.”

## Recommendation (start here)
Choose **Option B1: Static pre-generated per-species pages with SVG charts**.

Rationale:
- Matches your current architecture (Python + Jinja + static output)
- Deep-linkable pages are a real UX win from the table
- SVG keeps dependencies low and output deterministic/testable
- Aligns with “conservative signal system” — simple visuals, explainable stats

Suggested phased rollout:
1. **Phase 1 (MVP):** Create a per-species page with: title, back links, current signals/risks, last 12 history rows, one larger SVG price chart.
2. **Phase 2:** Add wishlist chart + bounded carryover notes.
3. **Phase 3:** Add size selector and per-size charts.
4. **Phase 4:** Add “from breeder table / from dealer table” backlinks and small “why” narrative.
